# 问答助手 v0.9 归档说明

> 阶段：需求验证 / 技术可行性（2026-10）
> 形态：单文件命令行原型，零第三方依赖
> 结论：检索能回答“标准是多少”，但不能回答“这张票能不能报、要补什么、找谁批”

## 1. 当时要验证什么

1. 制度只有 20 多页、切片后不到 100 段，是否值得上向量数据库？
2. 中文 2-gram + BM25 在“住宿标准/时效/审批”这类问题上，Top3 命中率够不够？
3. 回答带条款引用后，员工是否愿意相信？

## 2. 做了什么

| 能力 | 实现 |
|---|---|
| 切片 | 按 500 字、50 字重叠切分，保留小节标题 |
| 检索 | BM25（纯标准库实现）+ 关键词加权 |
| 回答 | 模板化摘取 Top3 条文，附条款号 |
| 交互 | 命令行多轮，支持 `退出`、`重置` |
| 评测 | 30 条问题，人工判定 Top3 是否含正确条款 |

## 3. 结果与局限

- 检索 recall@3 约 92%，但**金额问题仍需人工二次计算**：回答“500 元/晚”不等于算出“超标 280 元”。
- 无法校验发票（抬头、税号、查重、时效），也无法生成草稿。
- 纯检索没有“弃答”机制，制度外问题会硬凑条文。
- 没有权限、没有审计、没有确认闸门，不能直接给财务用。

## 4. 为什么演进为 MVP

原型证明了“检索可用”，也暴露了三个必须工程化的问题：

1. **规则要代码化**：金额/时效/标准不能靠模型或模板拼。
2. **动作要可中断**：建单必须人工确认。
3. **回答要可追溯**：引用、工具调用、确认人都要留痕。

这三条直接对应 MVP 的 `rules.py`、`confirm_required`、`agent_logs`。

## 5. 如何运行归档

```bash
python quickstart.py
# 或
python prototype/reimbursement_assistant.py
```

不需要 API Key、不需要安装依赖；数据来自 `data/policies/company_reimbursement.md`。
