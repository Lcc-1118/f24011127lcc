# 01 · 需求评审：十个最关键的问题

> 角色设定：十年经验的企业信息系统架构师。本文是立项评审的第一道关口——先问清楚，再画架构。
> 每个问题都给出"不同答案 → 架构差异"，这是评审真正的价值：不是收集需求，而是暴露决策点。

---

## 问题 1：报销单最终要不要真的提交给财务系统？

**为什么关键**：这决定了本系统是"咨询工具"还是"业务系统"。前者只需要知识库与对话；后者必须处理幂等、对账、失败补偿、状态机。

| 答案 | 架构差异 |
| --- | --- |
| 只做草稿，人工复制到 OA | 无需对接、无幂等要求，`drafts` 表就是终点，一周内可跑通 |
| 需要推送到 OA/ERP | 增加出站适配层（adapter）+ 重试队列 + 幂等键（idempotency key）+ 状态回写，周期翻倍 |
| 系统就是报销主系统 | 需要审批流引擎、电子档案、财务凭证对接，属于另一个量级项目 |

**本项目的选择**：只到草稿 + 审批链路预演，明确不做真实提交（写进一页纸需求的"非目标"）。

## 问题 2：制度知识库谁维护、多久变一次？

**为什么关键**：制度更新频率决定检索层是"静态索引"还是"带版本的多版并存"。

| 答案 | 架构差异 |
| --- | --- |
| 一年一版，财务手工改 | 单文档覆盖即可，重建索引即可 |
| 季度更新，多部门各写各的 | 需要文档版本、生效日期、按部门隔离、批量重建 |
| 政策频繁变动、需追溯历史 | 需要向量库版本化 + 生效日期过滤（按时点检索历史制度） |

**本项目的选择**：`policy_docs` 带 `version` / `effective_date` / `status`，同名上传自动把旧版置为 `archived`，检索只命中当前版；不做按时点回溯检索（列进后续迭代）。

## 问题 3：发票信息从哪来？

**为什么关键**：OCR 是独立的成本与准确率问题，会改变整个数据流与合规边界。

| 答案 | 架构差异 |
| --- | --- |
| 员工在对话里手动输入号码/金额/日期 | 无 OCR，纯文本抽取（正则），本期方案 |
| 上传图片由系统 OCR | 引入 OCR 服务、图片存储、识别置信度、人工复核队列 |
| 对接发票查验平台（税务） | 引入外部 API、验签、限流、失败降级，且需合规评估 |

**本项目的选择**：手输 + 正则抽取 + 规则校验；OCR 与查验平台列为"接入点已预留，本期不实现"。

## 问题 4：审批规则是"硬规则"还是"软建议"？

**为什么关键**：这是本项目最重要的架构判断——**数字类判定绝不能交给大模型**。

| 答案 | 架构差异 |
| --- | --- |
| 金额/时效/标准由大模型"判断" | 不可审计、不可复现、幻觉直接造成财务损失 |
| 硬规则由代码判定，模型只负责解释与引导 | 需要独立的 rules 层 + 工具化暴露给模型 + 单测覆盖 |

**本项目的选择**：`app/agent/rules.py` 是唯一裁判，输出带 `clause` 的结论；大模型只能引用工具结果。

## 问题 5：两个角色的权限边界在哪？

**为什么关键**：员工能看到自己的对话，管理员能看到全员对话——审计页天然是隐私敏感面。

| 答案 | 架构差异 |
| --- | --- |
| 只区分"能进后台/不能进后台" | 一层角色判断即可 |
| 员工只见自己、管理员可见全员并留痕 | 需要接口级鉴权 + 越权防护（他人会话按不存在处理）+ 审计日志 |

**本项目的选择**：JWT（httpOnly Cookie）+ `require_user` / `require_admin` 双守卫；查询他人会话一律 404，不泄露存在性。

## 问题 6：部署形态与数据落地在哪？

**为什么关键**：报销数据含金额、城市、行程，属于内部敏感数据；部署方式决定合规义务。

| 答案 | 架构差异 |
| --- | --- |
| 公有云 SaaS、多租户 | 需要租户隔离、加密、等保/审计合规，工期显著增加 |
| 单机内网部署（一台 VM） | SQLite 够用，备份=文件拷贝，本期方案 |
| 内网 + 数据库集群 | 需要迁移到 PostgreSQL/MySQL + 连接池 + 迁移脚本 |

**本项目的选择**：单机 + SQLite（WAL），预留 `db_path` 配置与仓储层边界，迁移成本可控。

## 问题 7：大模型供应商能不能换？要不要私有化？

**为什么关键**：把模型调用耦合进业务逻辑，是这类项目最常见的技术债。

| 答案 | 架构差异 |
| --- | --- |
| 锁定单一厂商 SDK | 供应商变更=全量改造 |
| OpenAI 兼容协议 + 可配置 base_url/model | 换供应商只改环境变量，本期方案 |
| 私有化部署模型 | 需要推理服务运维、显存规划、Token 成本模型重算 |

**本项目的选择**：`app/llm.py` 只实现 OpenAI 兼容协议，`LLM_BASE_URL`/`LLM_MODEL`/`LLM_API_KEY` 全可配；无 Key 时自动降级为离线规则大脑，保证演示与评测可复现。

## 问题 8：对话历史保留多久、要不要脱敏？

**为什么关键**：审计要求"可回溯"，隐私要求"最小化保留"，两者冲突需要显式决策。

| 答案 | 架构差异 |
| --- | --- |
| 永久保留全文 | 简单，但隐私风险随时间线性增长 |
| 保留 N 天后自动清理 | 需要定时任务 + 归档策略 |
| 保留但敏感字段脱敏（发票号掩码） | 需要脱敏层 + 检索时还原策略 |

**本项目的选择**：全量保留用于审计，但页面上发票号/税号做掩码展示；保留期与清理任务写进上线检查清单待财务与法务确认后启用。

## 问题 9：评测与验收标准怎么定？

**为什么关键**：没有量化验收，"智能体做完了"就会变成主观判断。

| 答案 | 架构差异 |
| --- | --- |
| 演示几个问题就算过 | 无回归能力，改一次提示词就可能全崩 |
| 固定评测集 + 自动跑分 | 需要 `evals/cases.json` + 跑分脚本 + 通过率门槛（本期 30 条） |
| 再加人工抽检与线上埋点 | 需要埋点、看板、抽检流程 |

**本项目的选择**：30 条用例（制度 10 / 工具 10 / 违规 5 / 多轮 5）+ 自动跑分脚本，当前 30/30；验收门槛定为"通过率 ≥ 90% 且陷阱题 100% 拒绝编造"。

## 问题 10：出现"模型说错了"时，谁来兜底、怎么回滚？

**为什么关键**：智能体系统的风险不在正常路径，而在异常路径。

| 答案 | 架构差异 |
| --- | --- |
| 靠员工自己判断 | 无兜底，投诉即事故 |
| 模型故障降级为"只给条文 + 提示人工判断" | 需要在编排层实现降级分支与提示语 |
| 全部结论强制人工复核 | 效率归零，但合规最强 |

**本项目的选择**：三层兜底——模型超时降级为纯检索结果、工具失败返回中文错误码、草稿必须人工确认才落库。

---

## 评审结论（进入下一阶段的前提）

1. 本期只做**草稿**，不做真实提交；OCR/查验平台不实现。
2. **数字与规则由代码判定**，模型只解释——这条不可谈判。
3. 单机 SQLite + OpenAI 兼容协议，供应商可替换，无 Key 可离线演示。
4. 验收以 30 条评测集的自动跑分为准，门槛 90%。
5. 详细范围见《02-一页纸需求清单.md》。
