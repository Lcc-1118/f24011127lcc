| **合计** | **30** | | |

对比前序版本（`_ref/reimbursement-agent` 的 25+5 条）：这版把"工具调用顺序"和"必须中断确认"变成**可断言字段**，不再靠人工看回答。

断言字段只有四个，刻意保持简单：

```jsonc
"checks": {
  "must_contain_any": ["500", "一线"],     // 回答里至少出现一个
  "must_not_contain": ["未找到"],          // 回答里不能出现（防"该答却说没找到"）
  "expect_confirm": true,                  // 必须触发 confirm_required（建单类）
  "turn_index": 1, "must_contain_any": …   // 多轮：只校验第 2 轮
}
```

`expected_tools` 用**子序列**匹配（`is_subsequence`），不是全等：允许中间多调工具（比如先 `search_policy` 再 `validate_invoice`），但不允许少调或调错顺序。这个设计来自一个具体判断——**"多查一次制度"是良性行为，"跳过校验直接建单"是恶性行为**，断言应该对前者宽容、对后者零容忍。

## 4. 评测抓到的两个真 bug（值得记下来）

### bug 1：中文紧贴数字时发票号抽不到

`_INVOICE_RE = r"\b(\d{8,20})\b"` 在"发票号12345678"上匹配失败——`\b` 要求"字"与"词"的边界，而中文字符在 Python 正则里属于 `\w`，`号` 和 `1` 之间没有边界。改成 `(?<!\d)(\d{8,20})(?!\d)`（断言前后不是数字，而不是词边界）后修复。**T06 就是为这个 bug 留的回归用例。**

### bug 2：制度问题被误判成发票校验

意图正则原先只要含"能报吗"就判 `validate`，于是"那超时了还能报吗"会去调 `request_invoice_info` 追要发票号——答非所问。修法是把判定改成**双条件**：

```python
if re.search(r"这个发票|这张发票|该发票|(?:这|那)(?:张|个)(?:发票|小票|票|呢)|校验|审核一下", q) or (
    re.search(r"能报吗|能不能报|可以报吗|能不能报账", q)
    and re.search(r"发票|小票|票据|这个|那个|\d{8,20}", q)
    and not re.search(r"标准|规定|要求|流程|时效|怎么算|是多少|多少|哪些|材料|多久|几天", q)
):
    return "validate"
```

即"必须指向某张票"+"在问能不能报"+"不是在问标准"。`M02` 与 `P05`（发票抬头必须是什么）就是这两个方向的守门用例。

## 5. 已知局限（评测通过 ≠ 可上线）

1. **用确定性大脑测的**：`run_eval.py` 跑的是 `HeuristicBrain`（无 Key）。真模型接入后，工具顺序可能不稳定，需要再跑一轮"真模型评测"才能说"模型也守规矩"。脚本已支持——配好 Key 即自动切换 `LLMBrain`。
2. **陷阱题只 3 条**，靠 `_OOS_TERMS` 词表命中。词表外的领域（"能报心理咨询费吗"）会漏判，表现为"硬凑条文"而不是"未找到"。这是当前最大的行为风险。
3. **断言是关键词级**，不是语义级。"回答含 500"不等于"回答正确使用了 500"。严格的评测应该做人审或 LLM-as-judge，MVP 阶段用关键词控成本。
4. **多轮只测 2 轮**，没测"6 轮后历史截断"的行为。
5. **金额边界未覆盖**：4999/5000/19999/20000 这四档审批门槛的边界用例还没写，是下一批该补的。
