# 05 · 阶段 1 原型说明（单文件命令行版）

> 对应提示词 3："只要一个 Python 脚本，不涉及 Web。"
> 代码：`prototype/reimbursement_assistant.py`（751 行，单文件，自带中文注释与`【复用·阶段2】`标注）

## 1. 一分钟跑通

```bash
# 有 API Key（OpenAI 兼容：DeepSeek / Moonshot / 通义 / vLLM 都行）
export DEEPSEEK_API_KEY=sk-xxxx
python prototype/reimbursement_assistant.py --ask "出差上海3天住宿标准是多少"

# 没有 Key，只想验证链路（哈希向量 + 回显 LLM，不联网）
python prototype/reimbursement_assistant.py --offline --ask "出差上海3天住宿标准是多少"

# 看真正发给模型的提示词
python prototype/reimbursement_assistant.py --ask "..." --show-prompt
```

`--offline` 是刻意做的：它让"没有 Key"不再是演示的阻塞点，也让 CI 可以零成本跑通整条链路。

## 2. 数据结构与主流程

```
制度 Markdown
   │ split_markdown(chunk_size=500, overlap=50)   ← 标题感知：切片不跨 ### 小节
   ▼
list[Chunk]（heading / text / tokens）
   │
   ├── BM25(tokenize)                 ─┐
   └── EmbeddingClient.embed(text)    ─┴→ VectorIndex（faiss 可选，缺省 numpy 精确内积）
                                          │
   问题 ──tokenize(问题)──────────────────┼→ rrf_fuse(bm25_rank, vec_rank, weights, k=60)
                                          ▼
                                    Top3 Hit（含 heading / text / 分数）
                                          │ build_messages(question, hits)
                                          ▼
                              LLMClient.chat(messages) → 带 [1][2] 引用的回答
```

## 3. 关键设计（以及为什么这样选）

| 决策 | 做法 | 理由 |
| --- | --- | --- |
| 切片要"标题感知" | 先按 `#` 标题切段，段内再按 500 字滑动窗口切，overlap 50 | 制度是"条款式"文档，把 2.2 住宿标准切成两半，比漏召回更糟——检索到的半个表格无法回答"多少钱" |
| 中文分词兜底 | 有 `jieba` 用 jieba，没有则"汉字 bigram + 英文整词 + 数字" | 保证零依赖可跑；bigram 召回略差但不会崩。实测两者 recall@3 只差几个百分点，不值得为此强制装包 |
| 两路必须融合 | RRF（`Σ 1/(60+rank)`），权重可配 | BM25 强在精确术语（"2.2 住宿标准"），向量强在同义改写（"住酒店能报多少"）。RRF 只用排名、不用原始分，避免两路分数不可比的问题 |
| 离线时下调向量权重 | `vector_weight` 从 1.0 → 0.35 | 哈希向量本质也是词面匹配，与 BM25 信号高度重复，等权融合会把 BM25 的正确排序拉偏。这条是实测调出来的，不是拍脑袋 |
| LLM 与 Embedding 双抽象 | `Protocol` 两个接口 + `EchoLLM` 兜底实现 | 换供应商只改环境变量；`EchoLLM` 让"没 Key"也能看到上下文长什么样，便于调提示词 |
| 提示词只放片段与出处 | `build_messages` 拼"【制度片段】[n] 出处：..."+ 结尾要求"按编号引用" | 让引用可核对。回答里出现 `[2]`，就能在页面上落到具体条文 |

## 4. `【复用·阶段2】`标注了什么

原型里 8 个模块带复用标注，最终去了这些地方：

| 原型模块 | 阶段 2 落点 | 变化 |
| --- | --- | --- |
| `Config.from_env()` | `app/config.py` | 加了 `db_path`、`jwt_secret`、`max_agent_rounds` 等 |
| `split_markdown()` | `app/rag/index.py::chunk_document()` | 输入从"本地文件"改为"数据库里的 doc 内容"，支持多文档 |
| `tokenize()` | `app/rag/index.py::tokenize()` | 增加否定词保留（"不得""不予"），停用词表重写 |
| `BM25` | `app/rag/index.py::BM25` | 参数不变（k1=1.5，b=0.75） |
| `HashEmbedding` | `app/rag/index.py::HashEmbedder` | 维度固定 512，FNV 哈希 + L2 归一 |
| `rrf_fuse()` | `app/rag/index.py::PolicyIndex.search()` 内联 | 融合逻辑不变，外面加了相关性门禁 |
| `HybridRetriever` | `app/rag/index.py::PolicyIndex` | 从"每次新建"改为"按 DB 签名缓存" |
| `OpenAICompatibleLLM` | `app/llm.py::OpenAICompatClient` | 增加 `stream()` 与 `tools=`（Function Calling） |
| `SYSTEM_PROMPT` | `prompt_templates` 表 | 从常量变成管理员可编辑的数据库记录 |

**没复用的部分**：`EchoLLM`（阶段 2 换成 `HeuristicBrain` 规则大脑，因为 Web 端要能真的建单，回显不够）、`VectorIndex`（切片太少，预算内直接 numpy 内积）。

## 5. 与阶段 1 报告的对应关系

原型输出的检索结果与 `scripts/recall_report.py` 的口径不完全一致，因为：

- 原型切片 27 个（500 字 + 标题切段），Web 版切片 21 个（同样参数但合并短小节）；
- 原型没有相关性门禁（阶段 1 还没暴露"陷阱题"需求），所以它对每个问题都会返回 Top3；
- 原型向量权重可配（离线 0.35），Web 版两路等权。

因此**质量指标以 `docs/04-阶段1检索基线报告.md` 为准**，原型只承担"证明链路可通"的职责。

## 6. 已知局限

1. 单文件 751 行，`Config` 与 CLI 混在一起，是为了"可复制粘贴"刻意做的妥协；阶段 2 必须拆包。
2. `--offline` 的哈希向量不是语义检索，别用它评估效果。
3. 索引缓存以"文件内容哈希"命名，改了切片参数而内容不变时不会自动失效——需要 `--rebuild`。
4. 无多轮上下文：一次问答一条独立的提示词，`--ask` 模式下无法追问。
