# 04 · 阶段 1 检索基线报告

> 对应提示词 3（裸问答原型）。回答一个问题：**不接 Web、不接数据库服务，纯命令行下"制度问答"能不能答对？**
> 复现命令：`python scripts/recall_report.py --json docs/recall-report.json`

## 1. 被测对象

| 项 | 值 |
| --- | --- |
| 语料 | `data/policies/company_reimbursement.md`（V3.2，119 行，21 个切片） |
| 切片策略 | 标题感知 + 500 字窗口 + 50 字重叠（`rag.chunk_document`） |
| 召回 | BM25（k1=1.5，b=0.75，中文 bigram 分词）+ 512 维哈希向量（FNV，L2 归一） |
| 融合 | RRF，`score = Σ 1/(60 + rank)`，两路等权 |
| 弃答机制 | 查询改写（口语→书面语）+ 业务词覆盖率门禁 + 域外领域词表 |
| 金标集 | 24 个"制度里有答案"的问题 + 5 个"制度里没有答案"的问题 |

## 2. 结果

| 指标 | 门禁开（线上实际） | 门禁关（仅对比） |
| --- | --- | --- |
| recall@3 | **95.8%** | 95.8% |
| recall@5 | **100.0%** | 100.0% |
| MRR | **0.969** | 0.969 |
| 域外弃答准确率 | **100%（5/5）** | 0%（0/5） |

**结论：相关性门禁在几乎不牺牲召回的前提下，把"该弃答时敢弃答"从 0% 提到 100%。**

## 3. 三个关键发现

### 3.1 召回早已不是瓶颈，**弃答**才是

第一版只有 BM25 + RRF、没有门禁时，24 个真问题的 recall@3 就已经 87.5%；但 5 个域外问题**全部**硬凑出了 Top5：

| 域外问题 | 无门禁时返回的 Top5 章节 |
| --- | --- |
| 公司有健身房补贴吗 | 3.2 发票合规、2.4 伙食补助、6.2 外地垫付、2.3 交通标准、1.1 适用范围 |
| 员工生日礼金能报销吗 | 6.3 出差生病、3.2 发票合规、1.1、6.5 驳回重提、4.2 审批时效 |
| 出差可以报销宠物托运费用吗 | 6.3、2.4、6.2、2.5 出差审批、1.2 报销原则 |

原因很直接：BM25 的分数只衡量"词重合"，而"健身房/礼金/宠物"这些词一个都不在制度里，能重合上的只有"公司/报销/出差"这类**到处都在的通用词**。所以模型永远有段落可引用，也就永远不会说"制度中未找到"——这正是企业知识库最危险的行为。

### 3.2 三道弃答闸门，各管一类问题

| 闸门 | 解决什么 | 具体做法 |
| --- | --- | --- |
| 查询改写 `expand_query` | 用户口语 ≠ 条文用词造成的**漏召回** | "报销时效是多久"→ 追加"费用发生日 90 个自然日内提交 报销时效"；"发票抬头"→ 追加"公司全称 纳税人识别号" |
| 覆盖率门禁 `_relevant` | 只靠通用词碰上的**假相关** | 剔除疑问词 bigram（吗/呢/怎/么）与通用词（报销/费用/发票/标准…）后，业务词命中 ≥2 且覆盖率 ≥1/3，或命中制度核心术语（时效/抬头/住宿/伙食…），或单命中且覆盖率 ≥1/2 |
| 域外领域词表 `_OOS_TERMS` | 制度**完全没覆盖的业务线** | 健身/礼金/宠物/年会/抽奖/休假/旅游/体检/团建/停车费等，命中直接返回空 |

分工很重要：覆盖率门禁处理"问得含糊"，领域词表处理"问得清楚但制度没有"。硬把它们合成一个分数阈值，两条都会失灵。

### 3.3 建立基线时抓到的两个真实假阴性

| 问题 | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 报销时效是多久 | 答"制度中未找到"（应命中 1.1） | 门禁要求"至少命中 2 个业务词"，而"时效"只命中 1 个 | 引入 `_CORE_TERMS`：命中核心术语单条即放行 |
| 哪些发票不能报销 | 答"制度中未找到"（应命中 3.3） | gate 里"发票"是通用词被剔除，只剩"哪些/些发"这类噪声 | 补查询改写："不能报销/不予报销"→ 追加"不得报销的票据 不予报销" |

修完后 recall@3 从 87.5% → 95.8%，MRR 从 0.885 → 0.969。

## 4. 与设计目标的对齐

| 目标 | 实际 | 判定 |
| --- | --- | --- |
| recall@3 ≥ 85% | 95.8% | 通过 |
| 陷阱题 100% 答"未找到" | 100%（5/5，含 3 条评测用例 P08–P10） | 通过 |
| 单次检索 < 200ms | 21 个切片单次 ~7ms（含改写与门禁） | 通过 |
| 无第三方依赖可跑 | 仅标准库 | 通过 |

## 5. 已知局限（写进放行清单，不掩盖）

1. **哈希向量不等于语义向量**：512 维 FNV 哈希只捕捉"词共现"，同义改写靠 `_QUERY_HINTS` 的人工词表兜底。制度新增业务线时要同步补词表，否则会出现新的假阴性。
2. **域外词表是硬编码清单**（`app/rag/index.py` 的 `_OOS_TERMS`）：它换来 100% 弃答准确率，但属于"白名单之外一律不认"的思路，无法泛化到未知话题。生产环境应换成"检索分数阈值 + 小模型判定是否成题"。
3. **金标集只有 24 条**，且由开发者自拟，存在"自己出题自己考"的偏差。真实上线前应采集 ≥ 200 条真实工单问题重跑。
4. 切片固定 500 字：制度里跨小节的规则（例如"审批链路"同时涉及金额与职级）可能被切断，靠 `heading` 前缀缓解但未根治。
